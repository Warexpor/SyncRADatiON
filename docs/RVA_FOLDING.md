# RVA folding (identical code folding) — patch audit

IL2CPP (and the linker behind it) folds methods with byte-identical bodies into ONE native function. `script.json` from
Il2CppDumper then lists several method names at the same RVA. Harmony patches native code, so a detour on one of them
fires for **all** of them: the patch body runs with a `this` of a foreign class, wrapped as the patched type. In the worst
case (an empty `Update`) that is every call of ~3,000 unrelated methods.

## Rules

1. A target whose RVA is shared with a **huge empty stub** (>= 50 names) is never patched. Replace the purpose with a poll or another hook.
2. A target shared with real instance methods starts with `if (!Il2CppRealType.Is<T>(__instance)) return/return true;` (`Sync/Il2CppRealType.cs`). First statement, before any other work.
3. Static folded targets have no `this`: nothing to guard, the patch must be idempotent/nested-safe (Dialoguer uses the nested-start guard).
4. After adding any `[HarmonyPatch]`: `scripts/rva_fold_scan.py --check` (needs the Il2CppDumper `script.json`, see the script header). If it reports a folded target, apply rule 1 or 2, then `scripts/rva_fold_scan.py --write` to regenerate this table and `tests/SyncRADation.Tests/Data/FoldedRva.txt`.
5. `RvaFoldingTests` (no Unity needed) scans the sources: a patch on any name in `FoldedRva.txt` fails the suite unless it is removed / guarded as listed.

Why the old `MultiKeyLock.Update` patch had to go: it is the empty stub at `0x2CB6B0`. Partial key packs now ride the existing 0.5 s puzzle poll (`MultiKeyLock` is registered in `PuzzleSyncService` and is a client-emit type).
